# open-browser 跨平台试用

Windows x64 下载 `open-browser-win32-x64.zip` 并完整解压，运行 `open-browser.cmd`。Linux x64 解压 `open-browser-linux-x64.tar.gz` 后运行 `./open-browser`。两个包内含 Node、浏览器引擎、扩展和本机服务。Linux 需要桌面会话及匹配 Chromium 的系统动态库。Ubuntu 构建机可用 `node node_modules/playwright-core/cli.js install-deps chromium` 安装系统库。macOS 使用签名应用 `open-browser.app`。

要从桌面启动，在 Windows 解压目录的 PowerShell 中运行 `powershell -NoProfile -ExecutionPolicy Bypass -File .\create-shortcut.ps1`，桌面会出现龙形图标的 open-browser 快捷方式。Linux 在解压目录运行 `./node/bin/node install-menu-entry.mjs`，即可从应用菜单搜索 open-browser。移动解压目录后，重新执行对应命令即可更新入口。Windows 便携包及源码安装的专用引擎都内置龙形窗口图标，直接运行应用也会在任务栏显示。


首次启动后，通过 CLI 或 MCP 创建工作区并打开页面。扩展新标签页显示正在运行的 Agent 和运行历史，受管标签可通过工具栏接管或交回。扩展提供缺少凭据时的绑定面板，macOS 应用额外提供原生底部悬浮条。

## 构建与验收

在对应的 x64 平台，`npm run build` 自动选取本机目标。构建环境需要 Node.js 22 或更新版本、Python 3、curl、tar 及 npm。运行 `npm ci` 后，在仓库根目录执行对应命令。

### 一键打包命令

这些命令按 profile 与 target 命名方式组织，构建、归档和 SHA-256 文件由同一个入口完成。

| 命令 | 用途 | 主要输出 |
| --- | --- | --- |
| `npm run package:macos` | 构建 Stable arm64 macOS 应用并生成 ZIP、DMG | `dist/open-browser.app`、`dist/open-browser-macos-arm64.zip`、`dist/open-browser-macos-arm64.dmg` |
| `npm run package:macos:dmg` | 只生成带 `Applications` 快捷方式的 arm64 DMG | `dist/open-browser-macos-arm64.dmg` |
| `npm run package:macos:arm64` | 显式构建 arm64 macOS 应用并生成 ZIP、DMG | `dist/open-browser-macos-arm64.*` |
| `npm run package:macos:x64` | 构建 x64 macOS 应用并生成 ZIP、DMG | `dist/open-browser-x64.app`、`dist/open-browser-macos-x64.*` |
| `npm run package:windows:x64` | 构建 Windows x64 便携包 | `dist/open-browser-win32-x64.zip` |
| `npm run package:linux:x64` | 构建 Linux x64 便携包 | `dist/open-browser-linux-x64.tar.gz` |
| `npm run package:portable:all` | 依次生成 Windows、Linux 便携包 | 两个平台的归档和校验和 |
| `npm run package:all` | 生成 macOS、Windows、Linux 全部本地发行包 | `dist/` 下全部平台归档 |

每次公开发行都要提供 Apple Silicon 和 Intel 两份 DMG。两个架构分别使用 `npm run build:release-macos:arm64` 和 `npm run build:release-macos:x64`。脚本先公证应用并固化票据，再对最终 DMG 签名、单独提交 Apple 公证并固化镜像票据。使用 `npm run release:verify-macos -- dist/open-browser.app` 和 `npm run release:verify-macos -- dist/open-browser-x64.app` 分别验收。`npm run package:macos*` 只用于本地安装测试。

开发构建使用 `npm run build:dev` 或 `npm run start:dev`。开发构建自动使用 `~/.open-browser/dev`，并隔离 PID、socket、回执数据库、Chromium profile 和 macOS 应用标识。稳定构建使用 `npm run build:stable` 或 `npm start`，数据目录为 `~/.open-browser`。

| 目标 | 构建 | 输出 |
| --- | --- | --- |
| macOS arm64 开发构建 | `npm run browser:install`，然后 `npm run build:macos:arm64` | `dist/open-browser.app`，需要 arm64 macOS 和 Developer ID Application 签名证书 |
| macOS x64 开发构建 | `npm run browser:install`，然后 `npm run build:macos:x64` | `dist/open-browser-x64.app`，需要 x64 macOS、Rosetta 下的 x64 Node，或 x64 CI runner |
| macOS arm64 GitHub 发行 | `npm run build:release-macos:arm64` | 已公证并固化票据的 `dist/open-browser-macos-arm64.dmg`、ZIP 及 SHA-256 |
| macOS x64 GitHub 发行 | `npm run build:release-macos:x64` | 已公证并固化票据的 `dist/open-browser-macos-x64.dmg`、ZIP 及 SHA-256 |
| Linux x64 | `node desktop/build-portable.mjs linux-x64` | `dist/open-browser-linux-x64.tar.gz` 和 SHA-256 文件 |
| Windows x64 | `node desktop/build-portable.mjs win32-x64` | `dist/open-browser-win32-x64.zip` 和 SHA-256 文件 |

在 Linux 或 macOS 运行 `shasum -a 256 -c 文件名.sha256`，在 Windows PowerShell 运行 `Get-FileHash 文件名 -Algorithm SHA256` 并与随附的 SHA-256 比较。便携包可在 macOS 交叉打包。在对应平台解压包后，进入解压目录，Linux 运行 `./node/bin/node verify.mjs .`，Windows 运行 `.\node\node.exe verify.mjs .`，检查实际归档能启动服务和扩展、创建工作区并通过 CLI 读取本地测试页面，再验证临时服务退出。

无需签名证书的贡献者可运行 `npm ci`、`npm run browser:install`、`node --test clients.test.mjs control.test.mjs engine-service.test.mjs`。Linux 和 Windows CI 还运行真实扩展登录、接管测试及解压后的服务验收。签名 macOS 构建机上运行 `npm run test:all` 和 `codesign --verify --strict --deep dist/open-browser.app`；检查实际可见标签打开、接管交回、普通标签不受影响及升级后登录态。正式发行运行 `npm run build:release-macos:arm64` 或 `npm run build:release-macos:x64`，它会用 `xcrun notarytool` 提交公证，执行 `xcrun stapler staple`，生成含票据的 GitHub DMG 和 ZIP，并运行 `npm run release:verify-macos` 验收 Hardened Runtime、票据、Gatekeeper 和两个归档的 SHA-256。

### macOS 签名与公证凭据

`desktop/sign.mjs` 默认启用可靠时间戳和 Hardened Runtime，并应用 `desktop/macos-entitlements.plist` 中 Chromium 所需的 JIT、未签名可执行内存和动态库加载权限。仅在离线开发调试时可设置 `OPEN_BROWSER_CODESIGN_TIMESTAMP=none`。正式构建不要设置该变量。签名身份可通过 `OPEN_BROWSER_SIGN_IDENTITY` 指定完整证书名称或 SHA-1。

公证凭据按以下顺序读取，密钥不会写入仓库。

1. 推荐使用本机钥匙串中的 notarytool 配置，设置 `OPEN_BROWSER_NOTARY_PROFILE`。可先运行 `xcrun notarytool store-credentials <profile>` 保存 API Key 或 Apple ID 应用专用密码。
2. CI 使用 App Store Connect API Key，设置 `OPEN_BROWSER_NOTARY_KEY`、`OPEN_BROWSER_NOTARY_KEY_ID`，团队密钥再设置 `OPEN_BROWSER_NOTARY_ISSUER`。`OPEN_BROWSER_NOTARY_KEY` 只接受 CI Secret 提供的 `.p8` 文件路径。
3. Apple ID 模式设置 `OPEN_BROWSER_NOTARY_APPLE_ID`、`OPEN_BROWSER_NOTARY_TEAM_ID` 和 `OPEN_BROWSER_NOTARY_PASSWORD`。也可把应用专用密码保存到钥匙串服务 `open-browser-notary`，脚本会按 Apple ID 账户读取。应用专用密码不能使用 Apple ID 登录密码。

脚本也兼容现有 GoLutra 发布环境的变量名。若本机已有 `~/.golutra-macos-release.env`，可运行 `source ~/.golutra-macos-release.env` 后直接执行发行命令。`APPLE_SIGNING_IDENTITY`、`APPLE_API_KEY_PATH`、`APPLE_API_KEY`、`APPLE_API_ISSUER`、`APPLE_ID`、`APPLE_PASSWORD` 和 `APPLE_TEAM_ID` 会自动映射到 open-browser 的发行流程。

当前发行目标采用 GitHub DMG 和 ZIP。若需改变产物路径，可设置 `OPEN_BROWSER_NOTARY_ZIP`、`OPEN_BROWSER_NOTARY_DMG` 或传入 `--zip`、`--dmg`。公证完成后，使用 `npm run release:verify-macos`，并保存构建提交、系统架构、DMG 和 ZIP SHA-256、notarytool Request ID 和验收日志。

## 发行记录

核对 `Docs/THIRD-PARTY-NOTICES.md`、分发内 `app/third-party-packages.json`、Node LICENSE、引擎的 ABOUT 与运行中的 `chrome://credits/`。保存构建所用提交、系统和架构、Node/Chromium 版本、包 SHA-256、测试输出与已知限制。CI 执行构建和验收；对外发布版本、选定项目许可证及上传 macOS 公证均由项目所有者决定。

在项目根目录运行 `python3 desktop/archive-release.py snapshot` 会生成保留执行位、固定时间戳的源码归档和校验和，包含 Git 已跟踪和未忽略的源码。归档保存在 `dist/open-browser-source-0.2.0.tar.gz`。macOS 构建机可以用以下命令归档已签名应用，再比对发行包中的应用源文件、第三方声明与源码快照。在此期间保持工作树稳定。

```sh
ditto -c -k --keepParent --sequesterRsrc dist/open-browser.app dist/open-browser-macos-arm64.zip
(cd dist && shasum -a 256 open-browser-macos-arm64.zip > open-browser-macos-arm64.zip.sha256)
python3 desktop/archive-release.py verify
```

验证通过后，`dist/SHA256SUMS` 记录源码和三个应用归档的完整 SHA-256。

### Dev 原生输入保护实验

使用已由 depot_tools 同步依赖的 Chromium 源码树，版本为 `159.0.8154.6`，提交为 `98a2592026af8d673b9fa83b626ac68bdf4ae78a`。在目标架构的构建机上执行以下命令。脚本检查提交、应用输入保护补丁、构建浏览器和 content_browsertests，再执行工作区输入过滤的原生回归。

```sh
node desktop/build-managed-input.mjs /path/to/chromium/src
```

在图形桌面的交互终端运行 `node benchmarks/managed-input.mjs <上一步生成的浏览器可执行文件>`。按屏幕提示点击主文档、跨源子文档和普通标签。测试还会输出关闭和启用保护时各 100 次 Agent 点击的 P50 与 P95。

在项目目录将 `OPEN_BROWSER_DEV_CHROMIUM` 设为上述可执行文件的绝对路径，执行 `npm run start:dev`。服务在临时浏览器资料中启动，通过扩展工具栏接管或交回工作区。未包含输入补丁的引擎会使用页面捕获层 `fallback` 输入锁定。只有显式设置 `OPEN_BROWSER_INPUT_GUARD=native` 时才要求引擎提供原生输入守卫。本实验的图形桌面验收和发行包验收须按平台记录。
